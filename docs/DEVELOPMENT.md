# Журнал разработки и воспроизведения (10 октября 2026)

Ниже — этапы, фактически пройденные при настройке двух CMP 50HX в одной системе. Это история диагностики, а не дополнительные обязательные действия для итоговой схемы.

## Шаг A — обнаружено ограничение одной карты

`clpeak` показывал GPU0 13.5 TFLOPS, GPU1 427 GFLOPS. Оба устройства определялись как `10de:1e09`, 56 Compute Units, 20 480 MiB, одинаковая версия драйвера/GSP `615.71.09`. VBIOS различались:

```text
03:00.0  90.02.60.00.1A   FP32 13.5 TFLOPS
84:00.0  90.02.60.00.01   FP32 0.427 TFLOPS
```

Обнаружена UEFI-запись `Boot0005* 50HX Unlock`, файл `/EFI/50HX/50HXUNLK.EFI`. В журнале уже имелось `*** UNLOCKED ... ***`, но первоначальная реализация разблокировала только одну карту.

## Шаг B — первая отдельная сборка под GPU1

Из `unlock50x_v1.c` в функции `u40x_find_gpu_pass(INTN enc)` добавлены временные ограничения:

```c
if (fastL[k][0] != 0x84) continue;
/* ... */
if (b != 0x84) continue;
```

Патч направлял поиск на вторую карту `84:00.0`. Сборка выполнилась с предупреждениями `CopyMem` о `const`, но потребовались два исправления toolchain:

- `EFI_LIB=/usr/lib/x86_64-linux-gnu` для `gnu-efi` на Kali;
- `--output-target=efi-app-x86_64` вместо `--target=efi-app-x86_64` для установленного `objcopy`.

Был получен `PE32+ EFI application`, подсистема `0x0a`, размер ≈1.7 MB. SHA-256 экспериментального фиксированного EFI:

```text
23761480da149a490b8f1410682228f0d5fa7027b2278a207b89676c5081da9d
```

Он размещён в отдельной директории ESP и был запущен через однократный `BootNext: 0006` без замены исходного EFI. После этого `clpeak` показал обратный результат — GPU0 ~426 GFLOPS, GPU1 ~13.6 TFLOPS. Таким образом, отдельная разблокировка второй карты доказана.

## Шаг C — два EFI за один GRUB-проход

Добавлен GRUB-пункт `CMP 50HX - UNLOCK BOTH GPUs (TEST)` с двумя вызовами `chainloader ... --return-to-grub`, а после них — повторным открытием `grub.cfg`. После ручного выбора тестового пункта обе CMP показали по ~13.5 TFLOPS.

Успешно подтверждена именно **последовательная**, а не параллельная разблокировка. Функциональность `--return-to-grub` предусмотрена upstream; сочетание двух разных EFI является экспериментальной оркестрацией.

## Шаг D — замена жёстких BDF на ordinal

Для повышения переносимости был создан вариант патча: удалить приоритетный `fastL`-цикл и выбирать `match_index++ == ordinal` перед сохранением `gBus/gDev/gFn`. Для ordinal 0 и 1 собираются **два разных файла**.

Это устраняет жёсткую привязку к `0x03` и `0x84`, но не гарантирует порядок после изменения оборудования или изменений upstream. Доказательство ограничено текущей конфигурацией и результатами `clpeak`.

Именно этот подход реализован в `scripts/patch_ordinals.py`.

## Шаг E — автоматизация следующей загрузки

Создан пункт GRUB `cmp50-auto`. В ОС установлен однократный systemd-сервис с `ExecStart=/usr/sbin/grub-reboot cmp50-auto`. Изменён BootOrder так, чтобы первым загружался Kali GRUB (`Boot0001` на тестовой системе). Сервис:

```text
ExecStart=/usr/sbin/grub-reboot cmp50-auto
status=0/SUCCESS
next_entry=cmp50-auto
```

Результат после успешной загрузки — 13.5 TFLOPS на обеих CMP. Важный нюанс: после запуска Kali systemd снова записывает `next_entry`, поэтому **само его наличие после загрузки не подтверждает**, что автоматическая разблокировка работала в текущем цикле. Критерий успеха — FP32 обеих CMP.

## Дополнительные аппаратные ограничения

PCIe-топология:

```text
GPU0 03:00.0 -> root port 00:02.0
GPU1 84:00.0 -> root port 80:02.0
nvidia-smi topo -m: NODE между картами, NVLink не обнаружен
```

`LnkCap` обеих CMP 2.5 GT/s x16; `LnkSta` GPU0 2.5 GT/s x4, GPU1 2.5 GT/s x16. Данный процесс compute unlock **не исправлял** PCIe.

## Особенность WPR2 / ёмкости памяти

В одном успешном запуске GPU1 журнал содержал:

```text
[50HX] using 10 GiB geometry (WPR2_LO=0x1ffffe00)
```

при том, что `nvidia-smi` видел 20480 MiB. У upstream отдельно описаны 20 GB-карты с нестандартными VBIOS/WPR2 latch и режимом `fb=20g`. Мы **не проверяли** влияние этого сообщения на работу с полными 20 GB, ReBAR или большие CUDA-аллокаторы. Не интерпретируйте успешный тест FP32 как полную валидацию видеопамяти.
